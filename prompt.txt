Context & Goal:
You are an expert Angular developer and software architect. Your task is to architect and write the code for "Pullboard," a local Angular developer utility that synchronizes upstream Pull Requests (from various code forges) with a JIRA Cloud sprint board.

The user is a backend systems developer who needs a streamlined way to turn unplanned upstream PRs into tracked JIRA tickets, link them to existing ones, and manage their lifecycle.

Architecture & Constraints:

    Framework: Latest Angular (Standalone components), Angular Material, Tailwind CSS.

    Execution & CORS: Do NOT build a separate backend server. The app must run locally via ng serve. You MUST configure a proxy.conf.json to bypass CORS restrictions for the Forge APIs (initially GitHub), JIRA Cloud REST API, OpenAI API, and Google Gemini API.

    Configuration: Do not implement OAuth. The app must read a local, git-ignored config.json file placed in the assets folder containing:

        forges: An array of forge configurations (e.g., [{ type: 'github', token: '...', apiUrl: '...' }])

        jira: Email, API Token, Base URL, Project Key

        llm: Provider (gemini or openai), API Key, Model Name (default to gemini-1.5-flash or gpt-4o-mini)

    Strict Rule (Read-Only Forges): This app has READ-ONLY access to the upstream forges. You must NEVER mutate, comment on, or alter the upstream Pull Request. All mutations happen strictly in JIRA.

Modular Forge Integration (Crucial):

    Unified Model: Define a UnifiedPullRequest TypeScript interface so the UI is completely agnostic to the backend forge.

    Strategy Pattern: Define an IForgeProvider interface with methods like getOpenPullRequests() and getPullRequestStatus(url). Implement GithubProviderService as the first concrete implementation.

    Factory/Service Registry: Create a central ForgeAggregatorService that reads the config.json, instantiates the correct providers based on the forges array, and aggregates PR data for the UI.

UI / UX Requirements:

    Theme: Default to a clean, high-density Light Mode using Angular Material components.

    Layout: A two-column dashboard.

        Left Column: Open PRs authored by the user, aggregated from all configured forges. Display a small badge/icon indicating the source forge. Draft PRs must be clearly badged.

        Right Column: The user's active JIRA tickets in the current sprint.

    Notifications: Do NOT use snackbars/toasts for success messages. When a PR is successfully synced, transform its UI card inline into a permanent success card with a large, highly visible HTML link to open the newly created/updated JIRA ticket in the browser.

Core Workflows:

Workflow 1: Create New JIRA Ticket from PR

    On an unlinked PR card (Left Column), provide a "Sync to JIRA" button.

    Clicking it triggers the configured LLM API (via proxy) to read the PR title and description, and suggest a JIRA Title, JIRA Description, and Story Points.

    Open an Angular Material Dialog pre-filled with the LLM suggestions for the user to review/edit.

    On confirm, the app calls JIRA APIs to:

        Create the ticket in the configured Project.

        Auto-assign it to the current user (look up the user's JIRA account ID based on the config email).

        Add the new ticket to the active Sprint.

        Add the PR URL to the JIRA ticket's "Web Links".

        Transition the JIRA ticket: If the PR is a Draft, transition to "IN PROGRESS". If Ready, transition to "REVIEW". (You must auto-discover the specific transition IDs from the JIRA project's workflow).

Workflow 2: Map PR to Existing JIRA Ticket (Drag & Drop)

    Implement Angular CDK Drag and Drop.

    The user can drag a PR from the Left Column and drop it onto an existing JIRA ticket card in the Right Column.

    On drop, immediately call JIRA APIs to:

        Add the PR URL to the existing JIRA ticket's "Web Links".

        Transition the JIRA ticket based on PR status (Draft -> IN PROGRESS, Ready -> REVIEW).

Workflow 3: Auto-Detect Closed PRs and Close JIRA Tickets

    For active JIRA tickets in the Right Column that contain PR URLs in their "Web Links", the app must use the ForgeAggregatorService to check the current status of those specific PRs.

    If the upstream PR is closed or merged, visually highlight the JIRA ticket card (e.g., distinct background color or border).

    Provide a prominent "Close JIRA Ticket" button on that highlighted JIRA card.

    Clicking it calls the JIRA API to transition the ticket to "DONE" or "CLOSED" (auto-discovered from the workflow).

Documentation Requirement:
You must write standalone Pullboard documentation in the mdBook format. Place the documentation in a docs/ folder in the root directory. It must contain:

    A book.toml configuration file.

    A src/SUMMARY.md file acting as the table of contents.

    Markdown files in src/ broken down logically (e.g., Installation, Configuration, Forge Providers, Architecture).
    Ensure the documentation clearly explains the config.json payload, the proxy bypass mechanism, and how to add a new Forge provider.

Deliverables:
Provide the complete setup instructions, the proxy.conf.json configuration, the config.json interface, the abstracted Forge interfaces (IForgeProvider, UnifiedPullRequest), the GithubProviderService, the JiraService, the LlmService, the primary Dashboard Component (HTML/TS) demonstrating the drag-and-drop, API integration, and closed PR detection logic, and finally, the initial mdBook documentation layout (book.toml, SUMMARY.md, and an installation markdown).
